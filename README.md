# SKiLL Support Bot

Постоянная поддержка Discord-сервера SKiLL. Отдельный бот, отдельная база знаний; INFO Bot и MIX Bot не изменяются.

## Что готово

- Анализ новых сообщений в Forum через OpenAI, без требования знака `?`.
- Решения `ANSWER / ADMIN / IGNORE`, контекст темы, история и проверенные знания.
- Карточки в `support-info`: одна карточка на ожидающее обращение, последующие сообщения обновляют контекст.
- Ответ Staff через **Reply на карточку** → украинский текст от имени бота в исходной теме → сохранение verified knowledge.
- `!bot текст` для Staff: черновик сохраняется в постоянной очереди, сразу удаляется из Discord, затем публикуется на украинском. В Forum — в текущей теме; при Reply — ответ на указанное сообщение. В `support-info` — только Reply на карточку.
- Разрешения проверяются по роли Staff и владельцу сервера. Сообщения Staff, ботов, webhook и системные сообщения не трактуются как обращения.
- Через 24 часа после обработки без нового содержательного обращения добавляется тег `Вирішено`. Без сообщения о закрытии, без архивирования/блокировки. Новое сообщение снимает тег. `WAITING_FOR_STAFF` автоматически не закрывается.
- SQLite хранит обращения, очередь, доставку, историю, логи, learned knowledge и embedding cache на Railway Volume.
- Повторная доставка при сбоях, дедупликация gateway-событий, восстановление необработанных заданий после рестарта.
- `/health` для Railway, предварительная проверка каналов, роли, разрешений и application ID.

## Запуск в Railway

1. Railway → **New Project → Deploy from GitHub repo** → `CorvusSkill/skill-support-bot`, ветка `main`.
2. К сервису добавить **Volume** с Mount Path **`/data`**. Это обязательно: без Volume бот в Railway не стартует, чтобы не потерять обращения и знания.
3. Вкладка **Variables**: добавить только в Railway, не в GitHub и не в сообщения:

   ```text
   DISCORD_TOKEN=<Bot Token нового Support Bot>
   OPENAI_API_KEY=<ваш OpenAI API key>
   ```

4. Код использует Node 24 и Dockerfile автоматически. Стартовая команда уже задана. Оставить **одну replica**, отключить **Serverless / App Sleeping**, если эта настройка включена. Публичный домен боту не требуется.
5. Добавить бота на Discord-сервер и предоставить доступ к Forum и приватному `support-info`.
6. В Discord Developer Portal → Bot включить **Message Content Intent**. Presence и Server Members intents не нужны.
7. В Forum должны быть теги из ТЗ, включая **`Вирішено`**. Отсутствующие категории выводятся в logs; без `Вирішено` запуск останавливается.
8. В Railway выполнить **Deploy**. В logs дождаться `SKiLL Support Bot ready`. Сервис должен пройти healthcheck.
9. Перед использованием провести живые тесты в Forum и Reply в `support-info` по списку ниже.

Требуемые права бота в Forum: View Channels, Send Messages, Send Messages in Threads, Read Message History, Embed Links, Manage Messages, Manage Threads. В `support-info`: View Channels, Send Messages, Read Message History. У `@everyone` доступ к `support-info` закрыт.

## Дополнительные Variables

| Variable | По умолчанию | Назначение |
|---|---|---|
| `OPENAI_MODEL` | `gpt-5.4-mini` | Анализ и классификация |
| `OPENAI_EDIT_MODEL` | тот же модельный профиль | Нормализация Staff |
| `OPENAI_EMBEDDING_MODEL` | `text-embedding-3-small` | Поиск learned knowledge |
| `DATA_DIR` | `/data` в Docker | Каталог постоянных данных |
| `RESOLVE_AFTER_HOURS` | `24` | Тег после тишины |
| `LOG_RETENTION_DAYS` | `30` | Хранение диагностических логов |
| `SUPPORT_ENABLED` | `true` | `false` временно отключает обработку, сохраняя соединение |

Если модель недоступна для вашего OpenAI-проекта, выберите в Variables доступную модель с Responses API и structured outputs. Ошибка анализа передаёт обращение Staff; ошибка перевода не публикует выдуманный ответ, сохраняет черновик и повторяет попытку. После нескольких неудач Staff получает диагностическое уведомление.

## База знаний

`knowledge/seed.json` — стартовые подтверждённые правила из ТЗ. Learned knowledge хранится в `/data/support.sqlite`, **не коммитится в публичный репозиторий**.

Ответы по банам, санкциям и персональным доступам сохраняются как `CASE`: не используются для других игроков. Для общей базы сохраняются только ответы, классифицированные как общая инструкция. При сомнении или ошибке классификации применяется `CASE`.

Все начальные источники передаются модели. Learned knowledge выбирается семантически по embeddings, до восьми релевантных записей. Автоматический ответ требует известных ID источников; конкретные административные решения дополнительно блокируются программными правилами.

`config.json → tournaments` пока пуст: официальные каналы следующих турниров не были предоставлены. Поэтому бот сообщает об отсутствии подтверждённой информации в своей базе и направляет в новости. При официальном анонсе можно добавить:

```json
{"name":"Официальное название", "channelId":"DISCORD_CHANNEL_ID", "official":true, "status":"ANNOUNCED"}
```

Допустимые статусы реестра: `ANNOUNCED`, `ACTIVE`, `COMPLETED`. Это только навигация, без регламента и данных MIX/FACEIT.

## Проверки

```sh
npm ci
npm run check
npm test
```

Автоматические проверки используют подставленные ответы модели и Discord-адаптер: проверяют логику, хранение и сбои, без реальных отправок и расходов на API. GitHub Actions выполняет их при push и pull request.

Живые контрольные сценарии перед запуском:

1. «Не могу получить CS2 Player» без `?`: категория ролей, ответ или уточнение.
2. «Меня забанили, почему?» → Staff, без выдуманной причины.
3. «Когда регистрация на следующий CS2?» → только официальная навигация/новости.
4. Реклама Discord → правило и support email.
5. Компьютерный клуб предлагает партнёрство → support email.
6. Предложение увеличить поддержку → реальная карточка Staff, без обещания реализации.
7. «Спасибо, всё получилось» → молчание.
8. Неясная проблема → один блок уточнений, затем Staff при отсутствии решения.
9. Сообщение Staff в Forum → молчание; `!bot` → украинская публикация, исходник удалён.
10. `Вирішено` после 24 часов; новое сообщение снимает тег; ожидание Staff не закрывается.
11. ADMIN → Reply Staff → ответ в Forum → следующий похожий общий вопрос использует verified knowledge.

## Практические ограничения

- Модель анализирует текст и сведения о вложениях; содержимое скриншота не распознаётся автоматически. Неясные случаи уточняются или передаются Staff.
- На первом запуске старые темы не получают массовых автоответов. После простоя проверяются новые сообщения в уже известных темах (до 1000 сообщений на тему за проход).
- Одновременные обращения обрабатываются очередью в порядке поступления. Это не искусственная пауза для игрока: скорость зависит от API и Discord.
- Доставка имеет постоянные квитанции и Discord nonce. Редкое аварийное завершение между отправкой и записью квитанции после истечения окна Discord nonce может дать повтор; абсолютная exactly-once доставка между двумя сервисами не гарантируется.
- Если в теме уже пять тегов, бот не удаляет категорию ради `Вирішено`: пишет диагностическую ошибку, требуется освободить один тег.
- При удалённом канале, ошибках прав или API очередь сохраняется и повторяет попытки. Не отправляйте тот же Staff-ответ повторно, пока устраняется сбой.
- Для защиты от потери learned knowledge регулярно делайте backup Railway Volume. Не запускайте несколько экземпляров с независимыми копиями этой базы.

Локально: Node 24, скопировать `.env.example` в `.env`, внести секреты локально, выполнить `npm start`. `.env`, база, логи и `node_modules` исключены из GitHub.
